**Providers/models.** `ModelRuntime.create({authPath, modelsPath, credentials, modelsStore, allowModelNetwork, refreshOnCreate})` (`P/.../model-runtime.ts:109-125, 217-268`). ## C. Proposed design

### C1. Config schema (versioned, layered, content-addressed)

```
ConfigDoc { schema:1, version: <monotonic u64>, scopes: {...} }
Layer (each scope holds sparse patches):
  global:    { providers{}, models{}, mcp{}, skills[]:BundleRef, prompts{}:BundleRef, settings{}, env{} }
  runner:    id runner-<id> → same shape, narrowed by os/arch (runner facts from hello: runnerws.go:50-59)
  workspace: keyed by runner-local path (identity is server-built: next/server/internal/runners/identity.go)
  session:   keyed by sessionId (created at session birth, frozen)
Provider: { id, template?, name?, api:{type, baseUrl, headers{}}, auth:{kind:"apiKey"|"oauth"|"env", secretRef?},
            models[]: {id, name, reasoning, contextWindow, maxTokens, input[], cost{}, reasoningLevels[],
                       optionMap{}, enabled}, modelOverrides{}, enabled }
  apiKey / headers secret values are never inline: `secretRef: "sec_<ulid>"`; `${ENV}` allowed.
McpServer: { name, enabled, exposure, toolExposure?, description?, timeout,
   transport: {kind:"stdio", variants:{default?:{command,args,env}, darwin?, linux?, win32?, runner-<id>?}, cwd?}
             | {kind:"http", url, headers{...secretRef}, oauth:{clientId?, clientSecretRef?, callbackPort?, scope?, clientName?, cimd?}},
   workspaceOverrides: Record<path, {enabled?, exposure?, toolExposure?}>   // pi's project-override semantics: mcp.md:34-42
SkillBundle / PromptBundle: { digest: "sha256:…", files:[{path, mode}] , skillName, description, scopeHint }  // CAS on server data dir
Env: { mode:"append", value }  // PATH-style, plus explicit per-OS map {darwin:{}, linux:{}, win32:{}}
```

Layer semantics: deep-merge maps by key (providers by id, MCP by name), **arrays replace**, `null` deletes. Required pi constraints are enforced _at publish_ (server rejects, like `validateMcpServerConfig` `P/.../mcp-servers.ts:152-200`): provider/model ids, `baseUrl` when custom models, reasoningLevels non-empty, no `sse`, stdio command non-empty. This is the single place where "complete vs sparse" (`Z/packages/provider/src/config/*`) becomes a strict pi shape, so the UI keeps its sparse objects and the server compiles them.

### C2. Server storage + encryption (Go)

- Directory: `<data>/config/{config.json, secrets.enc, bundles/<digest>/…}`. `config.json` atomic tmp+rename like `next/server/internal/local/settings.go:110`.
- Secrets: **age** (`filippo.io/age`) with an X25519 recipient derived from a key file `<data>/keys/config.age.key` (mode 0600, **outside** `config.json`); or stdlib `crypto/aes` GCM with a 32-byte key file and `crypto/rand` nonces. Constraint: `next/server/go.mod` currently has **one** dependency (`github.com/coder/websocket`), so the zero-dependency AES-GCM option (nonce‖ciphertext, HKDF subkeys per secret id, AAD = secret id + config version) is the lower-risk default; age is the choice if you want rotation/passphrase tooling for free. Never log or echo values; the browser only ever sees `hasSecret: true` + a masked hint.
- Push payload carries secrets **per runner** (filtered: provider secrets are sent only for providers enabled for that runner; `secretRef`s the runner isn't entitled to are dropped, and the runner reports `secret-not-provisioned` for that provider instead of failing the whole apply).

### C3. Runner link protocol additions

New frames (all text JSON, same envelope as `frames.ts:15-56`):

- S→R `config` `{revision, version, doc:{merged snapshot}, secrets:{name→value}, bundles:[{digest, skillName, files}]}` — full merged snapshot, never deltas; server keeps per-runner `appliedVersion` plus in-flight.
- R→S `configApplied` `{version, ok, errors:[{scope, path, code, message}], facts:{modelsByProvider, mcp:[{name, state, failureKind, toolCount, toolNames, authUrl?}], skills:[...], prompts:[...]}}`.
- S→R `reload` is not needed: version bump + new snapshot suffice.
- Reconnect: server compares its `version` with the runner's `lastAppliedVersion` sent in `hello` (extend hello, backward-compatible field) and pushes immediately if stale; otherwise the runner gets the newest snapshot right after `welcome`. A runner must be able to serve `getView` before the first push — it answers from its last persisted applied snapshot (cache in `<runner data>/applied-config.json`, secrets excluded).

Because both ends silently ignore unknown `t`, adding these frames is backward compatible today: server `default: c.logger.Debug(...)` (`next/server/internal/runnerws/runnerws.go:302-303`), runner `parseServerFrame` returns nil for unknown (`packages/next-runner/src/link/frames.ts:111-120`).

Partial failure: apply is per-item transactional. A bad provider is skipped with an error entry, the rest applies, and the ack is still `ok:true` with `errors[]` — matching pi's own "invalid entries are reported and skipped" MCP behavior (`docs/mcp.md:82`). A structurally invalid doc (schema) is `ok:false` and the runner keeps its previous snapshot; the server marks the doc "rejected by runner x" in the UI.

### C4. How the runner applies it to pi (new sessions only)

1. On `config` frame: decrypt into memory, materialize bundles into `<runner data>/bundles/<digest>/` (atomic dir rename), then build an **immutable `RuntimeConfig`** object (frozen), swap a pointer, write the applied cache, send `configApplied`.
2. Per new session (`createPiSessionWithGate`, `Z/packages/next-runner/src/engine/pi/piSessionFactory.ts:79-132`):
   - `SettingsManager.inMemory(mergedSettings, {projectTrusted:true})` instead of `create(cwd)`; settings include `defaultProvider/defaultModel/defaultThinkingLevel/enabledModels/defaultTools`, `enableSkillCommands`.
   - `ModelRuntime` created once per runner (as now, `piEngine.ts:118-120`) but with `modelsPath: <runner data>/derived/models.json` written from the doc and `credentials` = in-memory store; on every config swap: `refresh({allowNetwork:false})` then `setRuntimeApiKey/removeRuntimeApiKey` per provider diff; custom providers from the doc go through `registerProvider`. Existing sessions keep the runtime object they hold — this is the "old sessions keep config" guarantee _as long as_ per-provider key changes don't retire runtime keys (use one runtime per config generation, or copy the old runtime for old sessions; pi's `ModelRuntime` is cheap to `create()`).
   - `DefaultResourceLoader({cwd: workspace, agentDir: runnerPrivateAgentDir, settingsManager, additionalSkillPaths:[...bundleDirs], additionalPromptTemplatePaths:[...], extensionFactories:[gate, checkpoint, createMcpExtension({loadConfig: () => docToLoadedMcp(doc, workspace), ...})], noExtensions:true (or a fixed allowlist)})`; pass `systemPrompt`/`appendSystemPrompt` if user text is configured.
   - MCP: either `loadConfig` closure (per-session snapshot, no files) or write `mcp.json` into a per-session temp agent dir. OAuth callback config per server (`callbackPort`/`callbackUrl`) comes from the doc.
3. Frozen sessions: store `configVersion` in session metadata; on resume, rebuild the session with that generation if still cached, else the latest (documented behavior: resumed old sessions get latest config — acceptable because pi session files carry their own model/thinking).
4. Existing sessions are never mutated except model selection (which is already a session command, `piSessionOps.ts:196-210`).

### C5. Channel mapping: server becomes the owner

- `provider-settings.*`: all methods served **by the server** (apply the facade semantics: sparse overlay merge per provider, revision increment, then bump doc version + push). `getView` returns the _desired_ view compiled from the doc, merged with runner-reported **facts** (`configApplied.facts.modelsByProvider`: pi's actual available models, auth status). `lookupModelInfo` stays server-side (models.dev). `listRemoteModels`/`testModelConnectivity` need an **outbound** runner call: a server-initiated `call` (`Conn.Call`, `runnerws.go:326-376`) to a new runner method `provider-settings.listRemoteModels` / `testModelConnectivity`. Without that, both features must be disabled (UI degrades: test returns `provider-unavailable`).
- `model-selection.getView`: server answers from the doc + facts; keeps `effectiveSelection` contract (runner logic `modelViews.ts:106-155` is reusable in TS on the runner's facts).
- `mcp-sync`: server answers `loadMcpFromUserDirectory`/`saveMcpToUserDirectory` from the doc (user scope); `listWorkspaceMcpServerStatuses` is forwarded to the owning runner → runner returns `configApplied.facts.mcp` (+ re-connects on demand); OAuth start (`authorization.authorizationUrl`) is a runner-originated fact, polled exactly as today (`McpSettingsSection.tsx:84-90`).
- `skills.list/setEnabled/deleteSkill`: server-owned catalog from skill bundles + global/workspace layers. `deleteSkill` on a bundled skill deletes the _bundle reference_ in the layer (refuses built-ins). `getSkillReferenceCatalog` is forwarded to the owning runner (as today's `useSkills` path expects) or answered server-side from the doc for the draft (no sessionId) case.
- `nex-session.readWorkspacePresentation.slashCommands`: runner synthesizes from its loaded prompt templates + `/skill:` commands + a small builtin list (`enableSkillCommands`), i.e. the same list pi builds at `interactive-mode.ts:786-814` (templates `:789-793`, skills `:806-813`). Source `"custom"` vs `"builtin"`.
- `commands` channel: add a server stub (`{list → {commands: []}}`) so the settings page doesn't reject; MVP can map it onto prompt templates later.

### C6. Migration from `~/.pi/agent`

Recommended: **import once, then server is authoritative** (not "merge local as lower layer"):

- On first `hello` from a runner with `configImported != true`, server issues `call` `config.exportLocal` → runner returns `{settings (redacted keys names only), models.json, mcp.json (secrets replaced by `${NAME}` refs), auth.json keys}`; server creates a `runner`-scope layer and `secretRef`s (browser never sees values; `hasSecret` only). Runner writes a marker.
- Keep the _runner_ reading local `~/.skills`, `~/.agents/skills` only if you want "local always visible" — but that violates "server owns config"; for MVP set `noSkills:false` but add only bundle paths and let users import; the pi user dir still exists physically (`getAgentDir()` `P/.../config.ts:605-610`).
- Rationale: a lower local layer makes UI "why isn't my edit taking effect" undebuggable, and leaks machine-specific credentials into sessions the server thinks it owns. Offer "Import from this runner" as a one-shot action per runner, plus a "Local facts" read-only panel.

### C7. Security

- Per-runner _entitlement_: each `secretRef` has a `grants: ["*" | runnerId… ]` list; default a provider's secrets go to every runner where the provider is enabled; an admin can pin e.g. a personal subscription token to one machine. Bundle files are not secret but are integrity-checked by digest (runner verifies sha256 before use, refuses mismatch and acks `bundle-integrity`).
- Transport is WSS; secrets never appear in `getView` responses, logs, or `configApplied`.
- Runner stores secrets in memory only; optional `NEX_RUNNER_ALLOW_SECRET_DISK=1` for headless restarts (explicit).
- OAuth login flows initiated by the UI are runner-executed; the resulting token goes to the server as a `secret` (either through an authenticated `config.secretPut` call or a CLI, not through the browser), then distributed by normal push. Anthropic OAuth (Claude Pro) and Codex tokens are user-level subscriptions — grant to one runner by default.

### C8. Ordering diagram — "user edits provider in Settings"

```
Browser Settings → provider-settings.savePersonalProviderOverlay
  → Server: validate (strict pi shape) → overlay merge → new ConfigDoc version Vn (secrets re-ref)
  → (200) ProviderSettingsView(revision=rn)   [UI commits immediately; optimistic]
  → for each entitled connected runner R:
       S→R config{version:Vn, doc:merge(global,runner,workspace,session), secrets, bundles}
       R: materialize bundles → build RuntimeConfig → swap pointer → write applied cache
       R: ModelRuntime.refresh({allowNetwork:false}) + setRuntimeApiKey diff + registerProvider diff
       R→S configApplied{version:Vn, facts:{modelsByProvider…}}
  → Server: merge facts into per-runner catalog; bump model-selection + provider-settings revision
  → provider-settings.onDidChange / model-selection.onDidChange to browser (first-runner listen)
  → Composer model picker + Settings list show the new model
```

Latency = 1 RTT + pi refresh (local, no network; `allowNetwork:false` at `model-runtime.ts:863-880`). If a runner is offline: desired view still shows `pending apply`; when it reconnects, `hello.lastAppliedVersion < Vn` triggers an immediate push.
