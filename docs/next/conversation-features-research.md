# Conversation features in pi-based next-runner — implementation report

Scope: ZCode `feature/next` (`packages/next-runner`, `packages/ui`, `packages/shared/src/nex-protocol-v4`, reference `apps/nex-cli/packages/bootstrap/src/nex-protocol-v4`) and pi 1.3.0 (`packages/coding-agent`). All citations are `file:line`.

---

## 0. Two cross-cutting prerequisites

**(-a) Rows must carry identity/actions or no UI entry appears.**
`ConversationRowView` only renders edit when `row.entityId` exists (`packages/ui/src/v4/ConversationRowView.tsx:1286`, target built at `:992`), fork only when `onFork && entityId` (`:1373-1376`), and `ConversationTurnGroup` gates `onEdit={row.actions?.canEdit===true}` (`:617`, `:1262-1281`), fork/retry on `actions.canFork/canRetry` of the **latest** assistant segment (`:801-802`, `:1013-1014`). The runner's snapshot builder emits none of `entityId`, `productTurnId`, `visibility`, `actions` (`packages/next-runner/src/projection/snapshot.ts:208-241`), so today every feature below is invisible. Step 0 is: assign `entityId` (stable, e.g. `pi:<entryId>`), `productTurnId = turnId`, `visibility: "visible"`, and compute `actions` exactly like `materializeCommandRowActions` (`apps/nex-cli/packages/bootstrap/src/nex-protocol-v4/product-projection.ts:1182-1300`): `canEdit`+`editDisposition:"rewind"` only on the newest realUser row, `canRetry` only on the newest complete assistant with a user cause, `canFork` only on the last text segment of a `completedSuccess` turn (`:1288-1296`). Schema: `rows.ts:10-31`.

**(-b) History must be rebuilt from the raw pi branch, not `session.messages`.**
`Engine.history()` returns `toEngineHistory(open.session.messages)` (`piEngine.ts:201-204`), and `session.messages` is the _projected_ context (`agent-session.ts:1637-1639`), which after compaction drops summarized messages and after `branch()` drops the abandoned branch. Restore therefore loses rows and cannot show compaction markers. Rebuild from `sessionManager.getBranch()` (`session-manager.ts:1469-1483`) and project `message`/`compaction`/`branch_summary` entries explicitly (`session-manager.ts:439-470`).

## 1. compact

**UI.** Triggered by the composer slash parser (`packages/ui/src/v4/slashCommands.ts:79-81`, `/compact` or `/compress`) and the context-usage panel callback (`ConversationComposer.tsx:426`, wired at `SessionPane.tsx:3252-3260`). Dispatch path `SessionPane.tsx:2208-2288`: `type="compact"`, empty payload (`command.ts:150`), **no baseRevision** (not in `COMMANDS_REQUIRING_BASE_REVISION`, `command.ts:296-312`); if `inputRouting.mode !== "startNow"` it toasts `chat.compact.queued` (`:2222-2225`, `:2279`); rejections map `compactOperationLock` / legacy `activeTurn` to toasts (`:2273-2278`). UI reads only `availability.compact` (`snapshot.ts:151-160`) and marker rows: `ConversationRowView.tsx:1738-1768` renders status running/noop/cancelled/failed/completed(completedAuto) from `timelineMarkerPayloadSchema` `compact` (`rows.ts:333-342`, lane `assistantWork` `rows.ts:403-408`). Running state also drives the loading shimmer (`v4/chatLoadingVisibility.ts:26-33`, `activeWorks.kind="compact"`).

**Old CLI.** `goal-compact.ts:56-117`: dedupe against running `activeWorks.kind==="compact"`, `manualCompactControllers` WeakSet and any queued compact (`compactOperationLock`); busy or routing≠startNow ⇒ enqueue typed intent `kind:"compact"`, `text:"/compact"` (queue item, never a user row); idle ⇒ `startManualCompact` (`:121-147`) which installs an `AbortController` on `record.activeAbortController` (so Stop cancels it) and runs `submitPrompt("/compact")` in background (`:149-235`), then holds the queue on failure/cancel (`:196-215`). Marker lifecycle projection: one row per operationId, upserted running→terminal, `origin manual|auto`, `tokensBefore/After`, `summaryRef`, and `activeWorks` push/pop (`product-projection.ts:4565-4665`).

**pi.** `AgentSession.compact(customInstructions?)` at `agent-session.ts:2794-2917`: **aborts the current run first** (`:2795`), guards `Already compacted` / `Nothing to compact` (`:2805-2813`), emits `compaction_start` (`:2797`) then `compaction_end` (`:2908`, `:2921`), appends a `CompactionEntry` via `appendCompaction` (`session-manager.ts:1261-1287`; entry type `:91-105`) and returns `CompactionResult {summary, firstKeptEntryId, tokensBefore, estimatedTokensAfter?, usage?}` (`compaction/compaction.ts:105-114`). `isCompacting` at `:1628-1633`; `abort()` aborts compaction (`:2464-2475`); `prompt()` throws while compacting (`:2076-2080`). Events are currently dropped by the runner (`engine/pi/events.ts:8-83` has no `compaction_start/end/entry_appended`).

**Runner design.** State owner: `SessionRuntime` gets `compact: {operationId, status, tokensBefore?, tokensAfter?, sourceCommandId}` plus `queueItemId` for queued compacts. Add EngineEvents `compact_start{reason}`, `compact_end{result?, aborted, errorMessage?}`, and translate `entry_appended` where `entry.type==="compaction"` into a marker upsert (dedupe by operationId = commandId, like old CLI). Command flow mirrors old CLI: if `session.isCompacting` or a compact is queued → `rejected("compactOperationLock")`; if `isStreaming`/draining/held → append queue item `kind:"compact"` (delivery.admitted `queue`) and ACK accepted; else run `session.compact()` and emit marker running immediately (before await) so the UI sees it. Terminal mapping: resolve→`success` (+`tokensAfter = estimatedTokensAfter`), throw with `Nothing to compact`→`noop`, `aborted`→`cancelled`, else `failed`. On terminal, pop `activeWorks`, recompute availability/inputRouting, then drain queue if `autoDrain`; on failed/cancelled with non-empty queue set `autoDrain=false, pauseReason` (old CLI parity `goal-compact.ts:196-215`). `stop` must `session.abort()` and therefore cancel compaction (`piEngine.ts:264-275`). If implementation is deferred, return `{allowed:false, reasonCode:"compactOperationLock"|"idleCannotCompact"}` (mirroring `projection-state.ts:117-155`) instead of the current unconditional `{allowed:true}` (`snapshot.ts:94-103`).

## 2. forkAssistant

**UI.** Triggered from the assistant action bar `ConversationRowView.tsx:1373-1376` gated by `canFork` (`ConversationTurnGroup.tsx:1013-1014`); payload `{target:{rowId,entityId}}` (`command.ts:152`), CAS (`baseRevision`+`baseLogEpoch`, `:296-320`). Handler `SessionPane.tsx:2739-2761`: on `accepted|duplicate` and `ack.result.type==="forkAssistant"` it calls `onSessionCreated(childId)` → pane switches to child (same path as create, `:1198-1214`, `:1244-1249`). **No rows change in the parent.** ACK shape `{type:"forkAssistant", sessionId}` (`command.ts:371-378`).

**Old CLI.** `fork-edit-retry.ts:280-335` + guard `product-projection.ts:884-935`: target must be a `complete` assistant, last text segment of a `completedSuccess` turn, messageId resolvable, no compact active; then `forkStableConversation` copies the conversation only (parent runtime/queue/workspace untouched; `v4-bridge.ts:1164-1205`). Child gets title `Fork of <parent>` with `titleSource:"generated"` (`session-fork.ts:146-167`) and a `forkNotice` marker at head `{parentSessionId,parentRowId}` (`product-projection.ts:5012-5030`); the parent intentionally shows nothing (`:5015-5021`).

**pi.** No public `AgentSession.fork()`; the primitive is `SessionManager.createBranchedSession(leafId)` (`session-manager.ts:1632-1740`) which rewrites the root→leaf path into a **new session file** with new id, `parentSession` header, re-chained label entries and fixed `firstKeptEntryId`; `SessionManager.open(file)` gives an independent manager. (`AgentSessionRuntime.fork` at `agent-session-runtime.ts:262-360` does this but _replaces the active session_ — wrong for a running parent.) `createAgentSession({sessionManager})` then yields a child `AgentSession`.

**Runner design.** Resolve target row → pi entry id (see §0; match message by timestamp/role against `getBranch()`). Open a _second_ `SessionManager` on the parent file (read-only intent; the parent keeps appending), then `createBranchedSession(targetEntryId)`. Before creating the child session, `appendCustomEntry("nex.fork", {parentSessionId, parentRowId})` (`session-manager.ts:1290-1300`) so the child's restore path can synthesize the `forkNotice` marker; title `Fork of …`, `titleSource:"generated"`. Create/open the child, register it in `PiEngine.sessions`/`SessionMetaStore`, emit `sessionsChanged`, return `{type:"forkAssistant", sessionId}`. Parent is never aborted — but only allow when the target turn is terminal; otherwise reject `guard.forkTargetNotStable`. Compaction active ⇒ `guard.compactOperationLock`. **Caveat:** `createBranchedSession` deep-copies entries; the child is a true copy, matching old CLI, and the parent's later appends don't leak in.

## 3. retryTurn

**UI.** Wire exists but **no product entry renders it**: `ConversationRowView.tsx:243` (“产品 UI 不渲染普通重试入口”), `SessionPane.tsx:3397-3403` still passes `onRetry`, payload `{target}` (`command.ts:161`), CAS. Handler `SessionPane.tsx:2802-2830` only logs on non-accepted; no result is expected (old CLI returns `undefined`). Rows change via projection: old CLI emits `row.removed(fromRowId = edited turn's header)` then appends an `editRerun` turn (`product-projection.ts:1762-1838`, `rows.ts:64-69`).

**Old CLI.** `fork-edit-retry.ts:246-278`: resolve assistant row → its messageId (rewind anchor) **and** the canonical user intent _before_ truncation; `rewindConversationToMessage` (active-chain cut, `:99-115`), then re-send `intent.text` + stable attachments through `startCanonicalIntent` (`:337-385`); rejects non-latest assistant with `guard.latestAssistantRetryOnly` (`:78-84`).

**pi.** No retry API. Equivalent: `sessionManager.branch(entryIdOfUserMessage.parentId)` (`session-manager.ts:1579-1589`) then `session.refreshContext()` (`agent-session.ts:1425-1427`, which rewrites `agent.state.messages` from the projection) then `session.prompt(originalText)`. Must be idle: `isStreaming` guard; old CLI preempts (`session-flow.ts:410-436`), so runner should `abort()` and `waitForIdle()` first.

**Runner design.** Use the same internal `rewindTo(entryId)` primitive as §4: verify idle (abort if busy), branch to parent of the user entry, `refreshContext()`, emit `row.removed{fromRowId=header rowId of that turn}` + reset `currentTurn/currentResponse`, then start a new prompt with `origin:"editRerun"` equivalent (projection adds `turnHeader.origin="userInput"` today; add `editRerun` support) and a **new** `sourceCommandId`/`rootSourceCommandId` lineage (`rows.ts:101-135`). Because the UI never exposes retry, this is cheap to ship after edit; if skipped, keep `canRetry` unset.

## 4. editUserQuery

**UI.** Inline editor in the user row (`ConversationRowView.tsx:947-1019`), submit `editUserQuery {target,newText,attachments?,workspaceMode?}` (`command.ts:154-160`), CAS+row-targeting. Note `attachments` omission means “keep canonical attachments”, explicit `[]` means “delete all” (`SessionPane.tsx:2778-2788`). ACK: `{type:"editUserQuery", disposition:"rewind", sessionId}`; `blocked` carries `reasonCode`+`preview` and opens the conflict dialog (`ConversationRowView.tsx:1003-1009`); accepted ⇒ editor closes. **No navigation to a child session** (`SessionPane.tsx:2812-2814`). Timeline truncation is driven purely by deltas (`delta.ts:100`, apply semantics `apply.ts:90-118`), new turn then appends.

**Old CLI.** `fork-edit-retry.ts:120-217`: reject unless target is the latest realUser row (`guard.latestQueryEditOnly`, `:66-75`); preempt active turn (`:144-151`); `workspaceMode:"rewind"` runs `previewWorkspaceFileRewind` → fail-closed `guard.workspaceRewind{Unsafe,Ignored,Unavailable,ApplyConflict}` returning the preview (`:153-206`); then `rewindConversationToMessage` and `startCanonicalIntent` with new text (`:207-219`). Note v4 “edit” never forks any more (`command.ts:90-92` comment, ACK comment `:398-399`).

**pi.** Same rewind primitive as retry: `branch(parentOfUserEntry)` + `refreshContext()`; abandoned branch remains in the file but is invisible. `navigateTree` (`agent-session.ts:3994-4100`) also works (same file, optional summary) but adds branch-summary plumbing and extension hooks — prefer `branch+refreshContext`. The edit text is re-sent via `prompt()`. Workspace file rewind has no pi equivalent: runner can only implement `preserve`; for `rewind` return `disposition:"blocked", reasonCode:"guard.workspaceRewindUnavailable"` with a synthetic preview (`v4ConversationFileRewindPreviewResult` `transport.ts:758-768`).

**Runner design.** Resolve entity → entry; enforce latest-only and empty-input rejection (`proto.invalidPayload`); if `workspaceMode==="rewind"` reject blocked; abort if streaming; branch/refresh; emit `row.removed`; start prompt with the _new_ text in the **same** sessionId. `rootSourceCommandId` should point at the original canonical input so the UI keeps lineage. Ordering: emit `row.removed` before the new `user_input` event, and reset `nextRowId` monotonically (never reuse rowIds — `delta.ts:100` assumes monotonic). Edge: pi timestamps/entityIds of surviving rows stay valid because the branch preserves entry ids for retained entries.

## 5. Queue and busy-send routing

**UI.** Payloads (`command.ts:163-174`) all CAS: `sendQueuedNow{queueItemId}`, `editQueueItem{queueItemId,newText}`, `reorderQueueItem{queueItemId,beforeQueueItemId|null}`, `deleteQueueItem`, `setAutoDrain{autoDrain}`. Panel: `ConversationQueuePanel.tsx:25-37`, rows locked when `dispatch.state!=="queued"` (`:127-146`), compact items show `/compact` and hide Edit (`:134`, `:219`). Handlers: delete `SessionPane.tsx:2859-2877` (accepted|noop, then settles the pending command); **edit is implemented as delete + composer restore** — `handleEditQueueItem` calls `deleteQueueItem` with the queue item's revision, then restores text/attachments/config into the composer (`:2879-2938`, `resolveQueuedComposerRestore :419-439`); the `editQueueItem` command is **never dispatched by the UI** (grep: no call site). sendQueuedNow `:2942-2958` (scroll bottom, accepted|noop). reorder `:2960-2976`. resume `setAutoDrain(true)` `:2978-2990`; paused banner uses `queue.pauseReason` (`ConversationQueuePanel.tsx:236-260`).

Send-while-busy: composer derives the modifier-action from `config.followupMode` (`composer/followupModeSettings.ts:6-18`, `ConversationComposer.tsx:1369-1395`); `inputRouting.mode` only enables/disables submit (`ConversationComposer.tsx:1060-1096`); `mode==="choice"` pops the clear/keep confirmation (`SessionPane.tsx:2368-2376`, `ConversationComposer.tsx:1399-1411`) and sends `heldQueueDisposition` + `expectedHeldQueueItemIds` (`command.ts:92-95`). Delivery override is `sendText.requestedDelivery: "startNow"|"queue"|"guide"` (`command.ts:87`). Guide items are split out of the queue panel and rendered as pending user bubbles by `delivery.admitted==="guide"` (`pendingGuideProjection.ts:11-30`, `ConversationPendingGuideList.tsx:14-32`).

Item schema (`snapshot.ts:209-224`) = full intent (`input-intent.ts:41-62`: `sourceCommandId, queueItemId, clientId, kind sendText|sendGoalCommand|compact, text, attachments, delivery{requested,admitted,fallbackReasonCode}, order{admissionSeq,queuePosition?}, steer{state,…}, dispatch{state,reservationId?}, admittedAt, provenance`) plus `toolDisallowlist` and `dispatch.state ∈ queued|reserved|promoting`.

**Old CLI.** `queue.ts:71-283`: delete→`noop queue.itemMissing` when absent; edit→reject compact items (`:96-105`); reorder→`beforeQueueItemId=null` means tail; `setAutoDrain(true)` also re-arms the idle ready hook (`:131-144`); `sendQueuedNow` = reserve→promotion lease→abort barrier→markPromoting→start (compact/goal/text)→remove, rollback reservation on pre-start failure (`:165-283`). Busy admission routing in `session-flow.ts:184-311`: `requestedDelivery:"startNow"` acquires a foreground promotion lease, applies held disposition, preempts and starts with `requireIdle` (`:212-245`, `:256-275`); otherwise `applyHeldQueueDisposition` (`:105-137`) then Core `sendInput` decides started vs queued; guide is passed as `queueDelivery:"guide"` (`prompt-turn.ts:108-127`). `computeInputRouting` (`projection-state.ts:157-197`): compact→enqueue, verifying→enqueue, running→guide|enqueue by `followupMode`, completed+queue>0+!autoDrain→choice, else startNow.

**pi.** `prompt(text,{streamingBehavior:"steer"|"followUp"})` (`agent-session.ts:2058-2114`); `steer()`/`followUp()` (`:2241-2262`) push into Agent queues (`agent.ts:143-174`) with **no remove-by-id, no reorder** (only `clearSteeringQueue/clearFollowUpQueue/clearAllQueues`, `agent.ts:309-321`; AgentSession exposes `clearQueue()` returning both arrays, `:2428-2440`, and string getters `:2448-2455`). `queue_update {steering, followUp}` is emitted on enqueue/drain (`:1046-1052`, type `:202-207`). Steering messages are delivered at the next tool-batch boundary, follow-ups after the run would stop (`agent-loop.ts:176`, `:295-315`).

**Runner design.** Make the **runner own the queue**; never use pi's follow-up queue for normal queued text (it is unobservable/unreorderable and survives abort ambiguously). One item = one `QueueItem` shape above. `sendText` admission: idle & !compacting & `routing==="startNow"` ⇒ `prompt()` now, ACK `inputAccepted{delivery:"startNow"}`; running (`routing==="guide"`) ⇒ `session.steer(text)` and keep the item with `delivery.admitted:"guide"` until pi's `queue_update` drops it (or a matching `message_start`), ACK `guide`; running queue-mode / compacting / held ⇒ push runner item, ACK `queue` (`inputAccepted{delivery:"queue"}`), `inputRouting` computed identically to `computeInputRouting`. `requestedDelivery:"startNow"` while busy: abort → `waitForIdle()` → start, ACK `startNow`. Drain loop (single-flight): on `agent_settled` and `isIdle` and `autoDrain`, mark head `reserved`→`promoting`, start compact-or-prompt, remove on admission; freeze on abort with `autoDrain=false` (pauseReason `stopped`/`error`). `sendQueuedNow` = abort + promote that item (remove others' reservations). `deleteQueueItem` → noop `queue.itemMissing` if gone. `reorderQueueItem` mutates the array before anchor. `editQueueItem` mutate text in place (must never be exercised by current UI, but keep for protocol completeness). `setAutoDrain(true)` drains when idle. `queueEdit`/`sendQueuedNow` availability must follow phase (deny `sendQueuedNow` when not running, `compactOperationLock` while compacting).

## 6. Model-generated titles

**UI.** Only consumes `snapshot.meta.title/titleSource` (`snapshot.ts:173-178`) and the sessions-index `titleSource` (`sessions-index.ts:34-38`); rename is a user command (`renameSession`, `command.ts` tail). Sidebar override logic `mapSessionSummaryToTaskMeta.ts:45`.

**Old CLI.** Gated once per session, turn 0, interactive only, length ≥10 chars, provider ready, custom never overwritten (`session-title.ts:17-22`, `:140-165`, `:200-205`). Uses `titleGeneration.modelSelection` or session model, system prompt forcing a JSON `{"title":…}`, 3–7 words, 60s timeout, input capped 1200 chars, output capped 100 (`title-generation-sidecar.ts:18-46`). Result persists as a session title event → `meta` delta with `titleSource:"generated"` (`product-projection.ts:1888-1908`). `renameSession` writes `custom` and blocks later generated overwrite (`session-title.ts:260-275`).

**pi.** No auto-title. `setSessionName` appends a `session_info` entry and emits `session_info_changed` (`agent-session.ts:3972-3978`; `appendSessionInfo`/`getSessionName` `session-manager.ts:1304-1330`). Cheap-model calls: `ModelRuntime.completeSimple(model, context, options)` (`model-runtime.ts:751-753`) or `complete` (`:715-720`), context type `{systemPrompt, messages}` (`pi-ai/src/types.ts:771-775`).

**Runner design.** In `PiEngine.submit`, when `turnNumber===0` (track per session in meta), `titleSource!=="custom"`, text≥10 chars and no title generation in flight: fire-and-forget `titlePromise` (tracked so `dispose` can ignore). Pick `runtime.getModel(<titleGenSelection ?? session.model>)`; build `Context{systemPrompt: <port of SESSION_TITLE_SYSTEM_PROMPT>, messages:[{role:"user",content: input.slice(0,1200),timestamp:Date.now()}]}`; parse JSON `title`, fallback to first non-empty line, clamp to 100 chars. Re-read meta before persisting (drop if `custom`), then `session.setSessionName(title)` + meta `{title, titleSource:"generated"}` + `emitSessionsChanged` + push a projection `meta` update on the open runtime. On restore, metadata remains authoritative (pi's `session_info` is a fallback). Skipped when `titleGeneration.enabled===false` (mirror old config).

## 7. switchModelConfig / setFollowupMode mid-session

**UI.** `switchModelConfig` is not sent by `SessionPane` during a live session (only a comment at `:2703`); the desktop sends it via the service layer for the thought-level picker and automations (`packages/services/src/nex-agent/nexTaskServiceAdapter.ts:2714-2735`, `:2772-2792`), and model picks ride `sendText.modelSelection` instead (`command.ts:99`). `setFollowupMode{mode}` (`command.ts:218`) is fired whenever the app-level setting differs from `snapshot.config.followupMode` (`SessionPane.tsx:3060-3120`), with stale-retry CAS (`:3005-3060`). Effects visible in UI: `config.provider/model/thought`, `inputRouting` recompute, and a `timelineMarker modelChange` row (`rows.ts:354-370`; render `ConversationRowView.tsx:1770-1800`), plus `modelTransition` on registry fallback (`session-config.ts:29-40`).

**Old CLI.** `model-config.ts:76-140`: cross-model switches provider client then emits `ModelSelected` (projection updates config + mid-session marker); same model + new thought emits the same event; identical values → `noop config.unchanged`; unknown provider → failed `provider.notInRegistry`. `setFollowupMode` just flips runtime config + event (`steering.ts:1046-1076`, `queue.ts:146-155`).

**pi / runner design.** `switchModelConfig`: resolve via `runtime.getModel`, `session.setModel(model)` (`agent-session.ts:2507-2539`, appends `model_change` and validates auth) and `session.setThinkingLevel(clamped)` (`:2642`, helper already in `piSessionOps.ts:applyModelSelection`); update projection `config`/`modelSelection`, append a `modelChange` marker (from/to), persist meta model. `setFollowupMode`: store in meta (`SessionMetaStore`), set projection `config.followupMode`, recompute `inputRouting`; pi's `setFollowUpMode("all"|"one-at-a-time")` (`:2735-2741`) is unrelated drain granularity and should be left alone. Both need real `revision` CAS (currently the runner ignores `baseRevision` entirely, `v4/commands.ts:27-66`).

## 8. Recommended order & estimates

1. **Row identity + actions + real availability/inputRouting + CAS revision** (shared prerequisite; also fixes history restore from raw branch) — **3–4 d**.
2. **Runner-owned queue + busy routing (queue/guide/startNow/held) + queue controls** — **5–7 d** (covers §5, `sendQueuedNow`, delete/reorder/autoDrain; `editQueueItem` is protocol-only).
3. **compact** — **2–3 d** (event translation, marker lifecycle, queued compact, stop-cancel).
4. **retryTurn + editUserQuery** (shared rewind primitive) — **3–4 d** (edit adds blocked/preview path, attachments semantics, lineage ids).
5. **forkAssistant** — **3–4 d** (second SessionManager, child registration, forkNotice custom entry, fork title).
6. **Generated titles** — **1.5–2 d** (gating + cheap-model call + setSessionName + meta updates).
7. **switchModelConfig / setFollowupMode mid-session** — **1.5–2 d** (mostly wiring; `setFollowupMode` is ~0.5 d).

Total ≈ **19–26 engineer-days**; items 1–3 unblock a usable conversation surface, 4–5 complete the action bar, 6–7 are polish. Unsupported-by-pi items to keep behind availability/rejection codes: workspace-mode rewind for edit (`guard.workspaceRewindUnavailable`), `applyFileRewind` / `canRewindFiles`, and `queueEdit` (UI never sends it today).
